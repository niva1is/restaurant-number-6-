# QR Restaurant — Frontend

Клиент платформы цифрового обслуживания ресторана: гость открывает меню по ссылке стола (QR) и оформляет заказ без регистрации; кухня ведёт приготовление; официант получает готовые заказы и вызовы от столов; администратор контролирует стоп-лист и все заказы.

Стек: React 19 · TypeScript · Vite 8 · React Router 7 · Context API · localStorage (синхронизация вкладок)

| Роль | URL |
|------|-----|
| Гость (стол N) | http://localhost:5173/t/N |
| Корзина | http://localhost:5173/t/N/cart |
| Статус заказа | http://localhost:5173/t/N/order-status |
| Кухня | http://localhost:5173/kitchen |
| Официант | http://localhost:5173/waiter |
| Администратор | http://localhost:5173/admin |

По умолчанию `/` редиректит на `/t/1`.

> **Текущий режим:** данные хранятся на клиенте (React Context + `localStorage`). Несколько вкладок браузера синхронизируются. Подключение к REST API и WebSocket бэкенда — следующий этап (см. раздел «Связь с бэкендом»).

## Роли и экраны

| Роль | Маршрут | Возможности |
|------|---------|-------------|
| **Гость** | `/t/:tableId` | Меню по категориям, корзина, заказ без регистрации, статус заказа, вызов официанта |
| **Кухня** | `/kitchen` | Очередь заказов: `ACCEPTED → COOKING → READY` |
| **Официант** | `/waiter` | Готовые заказы: `READY → SERVED → PAID`, приём вызовов столов |
| **Админ** | `/admin` | Все заказы, стоп-лист (вкл/выкл блюда) |

Авторизации на фронте нет: доступ разграничен **разными URL**.

### Демо-сценарий (3 вкладки)

1. Гость: `http://localhost:5173/t/5` → добавить блюда → «Отправить заказ на кухню».
2. Кухня: `http://localhost:5173/kitchen` → «Начать готовить» → «Готово».
3. Официант: `http://localhost:5173/waiter` → «Подать» → «Оплачен».
4. **Админ:** `http://localhost:5173/admin` → видеть все заказы; переключить блюдо в «Стоп» — у гостя оно станет «Нет в наличии»
5. Гость на статусе заказа видит смену этапов; кнопка «Вызвать официанта» появляется у официанта.

Данные общие за счёт `localStorage` и событий `storage` / кастомных событий между вкладками.

## State machine заказа

```
ACCEPTED ──кухня──▶ COOKING ──кухня──▶ READY ──официант──▶ SERVED ──официант──▶ PAID
   │                  │                 │                    │
   └──────────────────┴─────────────────┴────────────────────┴──▶ CANCELLED
```

Переходы валидируются на клиенте (`OrderContext`): недопустимый переход не применяется (ошибка в консоли). После подключения API ту же схему будет проверять сервер (см. backend README).

## Функциональность

### Гость
- Цифровое меню: категории, блюда, описание, калорийность, цена, фото.
- Стоп-лист: блюда с `inStock: false` помечаются «Нет в наличии», кнопка добавления отключена.
- Корзина: изменение количества, удаление, итог.
- Создание заказа → переход на экран статуса.
- Таймлайн статусов: Принят → Готовится → Готов → Подан → Оплачен.
- Вызов официанта (без дубля активного вызова со стола).

### Кухня
- Список активных заказов (`ACCEPTED`, `COOKING`).
- Кнопки смены статуса по state machine.
- Блок «Готово к выдаче» (`READY`).

### Официант
- Активные вызовы столов с кнопкой «Принять».
- Заказы `READY` → «Подать»; `SERVED` → «Оплачен».
- Сумма и состав заказа.

### Администратор
- Стоп-лист: переключение «В наличии» / «Стоп» (сразу видно гостю во всех вкладках).
- Активные и завершённые заказы (стол, статус, состав, время).

## Данные на клиенте

| Ключ localStorage | Содержимое |
|-------------------|------------|
| `restaurant-orders-v1` | Заказы + вызовы официанта |
| `restaurant-menu-v1` | Меню и флаги стоп-листа |

Стартовое меню — `src/data/menuData.ts` (грузинская кухня: хачапури, хинкали, шашлык, харчо, чурчхела, вино). При первом запуске копируется в `localStorage`; дальше правится через админку.

Корзина живёт только в памяти вкладки (`CartContext`), при обновлении страницы сбрасывается — как у гостевой сессии до появления API.

## Связь с бэкендом

Бэкенд (отдельный репозиторий): REST `/api/v1`, JWT персонала, токен стола `X-Table-Token`, RabbitMQ + Socket.io для вызовов и статусов.

| Сейчас на фронте | Целевое подключение к API |
|------------------|---------------------------|
| Меню из `menuData` / localStorage | `GET /menu` |
| Стоп-лист в MenuContext | `PATCH /menu/dishes/:id/stop-list` |
| `createOrder` локально | `POST /orders` (+ `X-Table-Token`) |
| Смена статуса в OrderContext | `PATCH /orders/:id/status` |
| Вызов официанта локально | `POST /notifications/call-waiter` |
| Синхронизация вкладок через localStorage | Socket.io: `ORDER_*`, `NEW_WAITER_CALL`, `STOP_LIST_CHANGED` |
| URL `/t/:tableId` | QR → `/table/<token>` (см. `PUBLIC_APP_URL` бэкенда) |

Рекомендуемые переменные окружения фронта (после подключения API):

| Переменная | Пример | Назначение |
|------------|--------|------------|
| `VITE_API_URL` | `http://localhost:5000/api/v1` | Базовый URL REST |
| `VITE_WS_URL` | `http://localhost:5000` | Origin Socket.io |

В Vite они доступны как `import.meta.env.VITE_*`. CORS на бэкенде уже рассчитан на `http://localhost:5173`.

## Критерии приёмки (фронт, демо без API)

- [x] Гость открывает меню по `/t/:tableId` без регистрации.
- [x] Корзина и оформление заказа.
- [x] State machine на UI: кухня и официант двигают статусы по допустимым переходам.
- [x] Стоп-лист: админ снимает блюдо — гость не может его заказать.
- [x] Вызов официанта отображается на панели официанта (синхронизация вкладок).
- [x] Админ видит активные и завершённые заказы.
- [x] Мобильный UX гостевого меню.

После интеграции с API те же сценарии подтверждаются сквозным демо с бэкендом (заказ → кухня → официант → оплата, broker, JWT).
